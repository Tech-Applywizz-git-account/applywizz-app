Applywizz Mobile Developer Handbook

This is the definitive end-to-end guide for engineers working on the Applywizz staff mobile application. It explains what the app is, where each piece lives, how it talks to backends, when builds are produced for stores, and every dependency an engineer must understand before shipping a change.

Expo SDK 57 React Native 0.86 Package com.invoices.app / com.applywizz.app Version 1.1.1 Repo: applywizz-app

1. Overview

Applywizz Mobile (npm package name invoices-mobile, Expo slug invoices-mobile) is a React Native application built with Expo. It is the field and operations client for Applywizz staff: invoicing and billing workflows, clients, reports, incentives, expenses, disputes, payment alerts, and switching into adjacent product shells (Snackify inventory and Career Associate) when the signed-in user is entitled.

The mobile app is a thin client. Business rules, money movement, permissions, and persistence live in the Django API hosted at https://invoice-ge4q.onrender.com (production). The app never talks to payment processors or databases directly for invoice payment settlement; it calls Django under /api/v1/.

Repository split Live development for this app belongs in Tech-Applywizz-git-account/applywizz-app. A frozen backup of the tree may also exist as archive_mobile/ inside the original invoice monorepo. The Django backend and web admin remain in the invoice monorepo (backend/, frontend/).

2. Audience & principles

Who this document is for

  • Mobile engineers joining Applywizz who need a full mental model in one place.
  • Backend engineers who must understand what the client expects from auth, billing, and push APIs.
  • Release managers who run EAS builds and store submissions.

Engineering principles baked into this codebase

  1. API is source of truth. Screens fetch and mutate through Axios; do not invent local-only business state for money.
  2. Login must never block on push or Render wake-up. Warmup and FCM registration are fire-and-forget.
  3. Refresh is single-flight. Parallel 401s queue behind one token refresh; network failures on refresh do not wipe the session.
  4. Production builds never point at LAN IPs. Local Django is opt-in via EXPO_PUBLIC_API_MODE=local.
  5. Secrets stay out of git. google-services.json, keystores, service accounts, and .env are gitignored.

4. Quick start

Prerequisites

  • Node.js 20+ (CI uses Node 20)
  • npm
  • Expo Go on a physical device or Android emulator / iOS simulator
  • Access to a reachable Django API (hosted Render or local 0.0.0.0:8000)

Install and run (Expo Go / Metro)

git clone https://github.com/Tech-Applywizz-git-account/applywizz-app.git
cd applywizz-app
npm install
npx expo start --host lan --clear

Scan the QR code with Expo Go. For a local API, set in a local .env (never commit): 

EXPO_PUBLIC_API_MODE=local
# optional: EXPO_PUBLIC_API_HOST=192.168.x.x

Start Django so phones on the same Wi‑Fi can reach it:

cd path/to/invoice/backend
python manage.py runserver 0.0.0.0:8000
Firewall On Windows, allow Python through the firewall when prompted. Android emulators use 10.0.2.2 as the host loopback; iOS simulators use 127.0.0.1; physical devices need the machine LAN IP (auto-detected from Metro hostUri when mode is local).

7. Runtime boot sequence

  1. index.js imports background notification task module, prevents auto-hide of splash, registers App.
  2. App.js loads Poppins fonts, wraps tree in SafeArea → Auth → Workspace → Theme → Toast providers.
  3. Gate warms the backend (/api/v1/ping/), starts keep-alive, hydrates disk query cache.
  4. AuthProvider restores access + cached user from AsyncStorage; if present, shows app immediately and refreshes /auth/me/ in background.
  5. RootNavigator: no user → Login (and optional Register); with user → ProductHost by workspace.
  6. Push listeners attach; pending alert polling starts when appropriate; Android payment notification channel is ensured.
Why Home can paint fast after login Query cache hydration intentionally survives login. Bootstrap workers overwrite keys; wiping the cache on every login caused 30–60s cold Home waits.

One binary hosts three product navigators. Entitlements come from user.apps on the auth payload. Workspace id is persisted under AsyncStorage key applywizz.workspace.

If user.apps is missing/empty, the client currently defaults allowed apps to ["snackify"].

9. Authentication

Authentication is email-based against Django SimpleJWT-style endpoints under /api/v1/auth/. The login screen also supports authenticator OTP when the API responds with require_otp: true.

Happy path

  1. User submits email + password on LoginScreen.
  2. AuthContext.signIn → POST /auth/login/ with body { email, password } and optional otp.
  3. If require_otp, UI switches to 6-digit OTP grid; user resubmits with OTP.
  4. On success, response must include tokens.access, tokens.refresh, and user.
  5. Optional legacy_tokens are stored for dual-DB / legacy payment paths (X-Legacy-Token header).
  6. Client persists tokens, sets user, starts bootstrap worker, registers push token (non-blocking).

Session restore

Cold start with stored access token + user JSON shows the product UI immediately, then revalidates via GET /auth/me/. Unauthorized handler is wired to signOut.

Logout

UI clears first (instant navigation to Login). Background cleanup (best-effort, capped ~600ms): POST /auth/logout/ with refresh token, clear AsyncStorage keys, clear Snackify session, unregister push device.

Self-registration

Register screen is compiled in only when runtime extra allowSelfRegistration is true. That flag is derived in src/config/runtimeConfig.js: never on production APP_ENV, and only when EXPO_PUBLIC_ALLOW_SELF_REGISTRATION=true. Endpoint: POST /auth/register/.

10. Tokens & storage

owner_*Saved owner session during impersonation
applywizz.workspaceSelected product workspace

Axios authorization

  • Request interceptor attaches Authorization: Bearer <access> (skipped for login).
  • Also attaches X-Legacy-Token when legacy access exists.
  • On 401 (non-auth bootstrap URLs): single-flight POST /auth/login/refresh/ with { refresh }.
  • Rotated refresh tokens from SimpleJWT are written back to storage.
  • Only 401/403/400 on refresh force logout; network/5xx keep the session.
  • FormData uploads strip Content-Type so RN can set multipart boundaries.

11. Impersonation (“view as”)

Admins can start impersonation via POST /auth/impersonate/start/ with { user_id }. The client stashes the owner tokens under owner_*, persists the target user’s tokens, clears workspace + Snackify session, and continues as the target. Stop via POST /auth/impersonate/stop/ then restore owner tokens. A 404 means the deployed backend is missing impersonation routes — point at a newer API.

12. API client

Central module: src/api/client.js.

  • resolveApiOrigin(): if extra.apiMode === "local" → http://<host>:8000; else extra.apiUrl or Render default.
  • API_BASE = ORIGIN + /api/v1
  • Default timeout 20s; some billing calls raise to 30–60s.
  • createMobileBalancedAdapter in requestLanes.js limits concurrent pressure on slow networks.
  • networkLog.js attaches debug logging for the in-app network log screen.
  • warmup.js pings /api/v1/ping/ and keep-alives hosted Render free-tier cold starts.

16. Push notifications

Detailed operational guide: PUSH_NOTIFICATIONS.md. Summary for developers:

  • Production path: Django firebase-admin → FCM HTTP v1 → device system tray (works backgrounded/killed on proper EAS builds).
  • App registers native token via getDevicePushTokenAsync after login (src/notifications/push.js).
  • Android package in Firebase must match com.invoices.app; place google-services.json locally before EAS Android builds.
  • Expo Go on Android (SDK 53+) cannot receive remote FCM; app polls /notifications/alerts/pending/ while open.
  • Payment-received copy targets owning staff; tap routes toward invoices.
Rebuild required Adding or changing google-services.json requires a new native build. A Metro reload is not enough.

19. EAS builds — where, how, when

Where builds happen

Native binaries are produced on Expo Application Services cloud builders, not on developer laptops (except local expo run experiments). Configuration: eas.json + app.config.js. Expo account owner: applywizz. EAS project id is embedded in config (overridable via env).

How to trigger

# from repo root (this app)
npm install
npx eas-cli login   # if needed
npm run eas:preview:android
npm run eas:preview:ios
npm run eas:play:build
npm run eas:ios:build

Equivalent direct CLI:

eas build --platform android --profile preview
eas build --platform ios --profile ios-store
eas build --platform android --profile production

When to build which profile

  • After JS-only fixes for QA: often Expo Go or an existing preview install is enough.
  • After native dependency / plugin / google-services / permissions change: new EAS build required.
  • Before Play Store release: production → Android App Bundle.
  • Before App Store release: ios-store with remote credentials.
  • Screenshot campaign: store-screenshots with demo fixtures enabled.

Artifacts

  • Android preview/dev: APK (buildType: apk)
  • Android production: AAB (app-bundle), credentialsSource local for Play keystore wiring
  • iOS store: distribution store, remote credentials, medium resource class

20. Store submission

npm run eas:play:submit    # Android internal track draft (service account file required locally)
npm run eas:ios:submit     # iOS via ASC app id in eas.json

Play submit expects ./google-service-account.json (gitignored). iOS submit profile ios-store references App Store Connect app id 6807382724. Privacy manifests and usage strings are declared in app.config.js (photo library, camera copy, required-reason APIs). Run npm run audit:ios:privacy before iOS compliance reviews.

25. New developer onboarding checklist

  1. Clone applywizz-app; read this handbook and SYSTEM_ARCHITECTURE.md.
  2. Install Node 20; npm install; run Expo against hosted API first (proves auth works).
  3. Obtain a non-production staff test account (ask an admin — do not share production passwords in chat).
  4. Optionally wire local Django from the invoice monorepo with EXPO_PUBLIC_API_MODE=local.
  5. Skim src/api/client.js and AuthContext.js before touching networking.
  6. For push work, read PUSH_NOTIFICATIONS.md; use a physical Android device + EAS preview build.
  7. Never commit .env, google-services.json, keystores, or service accounts.
  8. Before PR: npm test; for native changes, coordinate an EAS preview build.
  9. API contract changes: open a paired PR on the invoice backend when required.

Server-side billing intent resource manipulated from Create Billing / inbox flows.

Secondary JWT used to reach legacy payment data paths via X-Legacy-Token.
